# Stage 1A — `brands.website_url`

**Status:** shipped, 2026-07-29. Executes Stage 1A of
[`docs/executing/brand-hub-implementation.md`](../executing/brand-hub-implementation.md),
against `main` at **1.8.0**.

One nullable column, end to end: schema → migration → mapper → queries → wire →
two forms → two surfaces. It is deliberately the smallest useful thing in the
plan, and its real job is to **put a real migration through the release path
before anything interesting depends on one** — Stage 2 lands a table with a
hand-authored CHECK constraint, Stage 3 lands another plus a paid vendor, and
neither is a good place to discover that `scripts/migrate.mjs` is broken again
(it was, for releases v7 and v8).

**Not shipped here:** 1B (guideline-section provenance). Stage 1 releases as
**1.9.0** when 1B lands; the changelog is untouched by this pass.

Test baseline: **527** (517 passed, 10 skipped) → **557** (543 passed, 14
skipped). **+30 tests, and the 4 extra skips are this pass's own live-Postgres
file**, which runs — see Verification — but is skipped by the default `pnpm test`
because it has no `DATABASE_URL`.

## What changed, and why, layer by layer

### `packages/shared` — the schema, and the one line that matters

`BrandWebsiteUrlSchema` is new, exported, and used by all three brand schemas
rather than restated in each:

```ts
export const BrandWebsiteUrlSchema = z.url({ protocol: /^https?$/ }).max(2048)
```

**The protocol filter is the whole schema; the URL parse is decoration.** The
plan said `z.url()`, not `z.string()`, because this value is rendered into an
`href`. That is correct as far as it goes, and it is not sufficient — measured,
not assumed, against the installed **zod 4.3.6**:

| input | `z.url()` | `z.url({ protocol: /^https?$/ })` |
| --- | --- | --- |
| `https://casavostra.com` | pass | pass |
| `javascript:alert(1)` | **pass** | reject |
| `data:text/html,<script>` | **pass** | reject |
| `ftp://casavostra.com` | **pass** | reject |
| `casavostra.com` | reject | reject |

`javascript:alert(1)` *is* a syntactically valid URL — `new URL()` parses it
happily — so a bare `z.url()` would have shipped a stored XSS with a nice UI
around it, which is precisely the failure the plan named and precisely the check
that would not have caught it. The scheme restriction lives on the shared schema
so create, update and the row itself are all restricted **by construction**,
rather than by each remembering to be.

`.max(2048)` is the conventional practical URL ceiling; the column is `text` and
would otherwise take an unbounded string.

- `BrandSchema` gains `websiteUrl: BrandWebsiteUrlSchema.nullable()` — required
  key, nullable value. `BrandSummarySchema` extends `BrandSchema`, so the
  workspace grid gets it with no second fetch and no second declaration.
- `CreateBrandInputSchema` / `UpdateBrandInputSchema` gain it as
  `.nullable().optional()`.
- `UpdateBrandInputSchema`'s `.refine` widens to accept a **website-only** patch.
  Before this pass `{ websiteUrl: … }` alone was rejected as "no keys", which
  would have made the field unsettable from anywhere that does not also send a
  name.

### `packages/db` — migration 0003, and the `undefined`/`null` distinction

**Migration `0003_known_puck.sql`** is one line, generated by `drizzle-kit` and
read by hand before committing:

```sql
ALTER TABLE "brands" ADD COLUMN "website_url" text;
```

Additive and nullable, so **the previous image tolerates it**: drizzle builds its
select lists from the schema definition, so an older server simply does not ask
for the column, and its inserts leave it null. Rollback stays free for this
stage — stated rather than assumed, as the plan's risk table requires.

No CHECK constraint on the column. The `http`/`https` rule has exactly one
enforcement point (the wire boundary) and one writer; a second copy in SQL would
be a rule to keep in sync, not a belt-and-braces. This is a deliberate contrast
with 2A's `brand_assets_source_exactly_one`, where the constraint guards an
invariant *across three columns* that a future writer could plausibly violate.

`rowToBrand` carries the column; `listBrandSummariesByWorkspace` selects it.
**That query is the hazard in this layer** — it is the one brand read built from
a hand-written select list rather than `select()`, so a new column is silently
dropped there and nowhere else. There is a live test for exactly that.

`updateBrand` takes `websiteUrl?: string | null` and keeps the existing
conditional-spread idiom:

```ts
...(input.websiteUrl !== undefined ? { websiteUrl: input.websiteUrl } : {}),
```

**`undefined` leaves the column alone; `null` clears it.** A `?? null` anywhere
in that chain turns every rename into a silent website delete, and no existing
test would have failed. There are now three tests that would (db live, server
route, and the in-memory fake's own mirroring of the rule).

### `packages/server` — the wire boundary

`POST /workspaces/:id/brands` forwards `body.websiteUrl ?? null`. `PATCH
/brands/:id` already forwarded the validated body wholesale, so it needed no
change — the widened `.refine` and the shared schema do the work.

`test-helpers.ts`'s in-memory `createBrand`/`updateBrand` mirror the real
`set()` semantics, including the `undefined`-vs-`null` rule. A fake that spreads
`input` wholesale would agree with a broken implementation, which is why the
live-DB test exists alongside it rather than instead of it.

### `packages/web` — two forms, two surfaces, one helper

**`src/lib/website-url.ts` is new** and holds both URL helpers:

- `normalizeWebsiteUrl(input)` — trims; treats empty as `null` (that is how you
  *clear* a website, not an error); prefixes `https://` when the value carries
  **no scheme at all**; then validates with `BrandWebsiteUrlSchema` — the same
  schema the server enforces, not a second hand-rolled rule that could drift.

  The scheme test is deliberately broader than `http`/`https`
  (`/^[a-z][a-z0-9+.-]*:/i`): the question it answers is *did the user supply a
  scheme*, and a bad one must survive to be **rejected** rather than be prefixed
  into `https://javascript:alert(1)`. Adding what is missing is normalisation;
  reinterpreting what is there is the share-URL rewriting the assets proposal
  lists as a non-goal.

- `displayHost(url)` — **moved here from `BrandIdentity`**, because `BrandCard`
  now renders the same host and a card importing from the hub's identity band to
  borrow a string helper is the wrong direction of dependency. Its three tests
  moved with it; that is the only existing test body this pass relocated.

**`NewBrandDialog`** (inline in `routes/workspaces.$wsId.index.tsx`) and
**`RenameDialog`** both gain `Website (optional)`, both route through
`normalizeWebsiteUrl`, and both render an inline error rather than firing the
mutation. `RenameDialog` is the brand's **only** edit surface — without the field
there, a brand created without a website could never acquire one.

The client check is a courtesy, not the defence: the server rejects the same
input with a 400 either way. What it buys is that the user is told *in the form*
instead of through a toast carrying a raw zod message, and that `casavostra.com`
— what people actually type — is accepted instead of being pedantry.

**`BrandCard`** renders the host as **text, not an anchor**. The whole card is
already a `Link` to the brand with a `before:absolute before:inset-0` overlay, so
a nested `<a>` would be invalid HTML *and* sit underneath that overlay:
announced to a screen reader as a link, unreachable with a mouse. The hub is
where the website becomes a real link; on the card it is an identifying fact.

**`routes/brands.$brandId.tsx`** feeds `websiteUrl={brand.websiteUrl}` and
`initialWebsiteUrl` to the rename dialog. `BrandIdentity` already rendered the
link — 1.8.0 built it against a fixture — so **the component did not change
shape, only its source of truth**, which is what the mockup pass was for.

## The invariant, half retired on purpose

1.8.0's load-bearing protection was:

> The real route can only pass `null` / empty for every prop this pass adds, and
> every new affordance renders nothing when its prop is absent.

**This pass retires the first half, for exactly one prop.** The route now passes
real data for `websiteUrl`, because that is what shipping means. The second half
does not retire and is what carries the weight from here — a brand with no
website renders no link, and that state is byte-identical to 1.7.0. It has a
test in `BrandIdentity.test.tsx`, one in `BrandHubView.test.tsx` (the whole
`absent-prop invariant` describe still passes untouched) and one in the new
`BrandCard.test.tsx`.

`colors`, `logoSrc`, `research`, `railVariant` and `tiles` are **still** unfed by
the real route. The comment blocks on `BrandHubView`, `BrandIdentity` and
`brands.$brandId.tsx` were updated to say which half of the invariant now applies
to what, so the next pass does not read a stale promise.

## What the live pass changed

**A live pass was run**, and it earned its keep on the first screenshot.

Playwright was installed **outside the repo** (scratch dir, `npm i playwright` +
`playwright install chromium`) — `package.json` and `pnpm-lock.yaml` are
unchanged, same approach 1.8.0 took. The app ran fully locally: `docker
compose -f docker/compose.yaml up -d`, `db:migrate`, `db:seed`, then the real
server (`AUTH_PROVIDER=local`, `local-disk`, `native-ws`) and `vite dev`, signed
in with the seed's dev token. 12 screenshots — 6 states × light/dark at
1600×900, plus a 900px pass — no console errors, no page errors.

**The bug it found:**

```
before   Add a descriptioncasavostra.com ↗
after    Add a description
         casavostra.com ↗
```

`BrandIdentity` renders the description as a `<p>` — a block — or, when there is
none, as an inline `<button>` offering `Add a description`. The website link is
an `inline-flex` anchor. **Two inline-level elements share a line**, so for a
brand with a website and no description the two ran together with no space
between them. A brand *with* a description hid it completely, because the `<p>`
pushed the link onto its own line.

1.8.0 could not have caught this: its fixtures paired a website with a
description in every scenario that had one, so the failing combination was never
on screen. Fixed by wrapping the anchor in a `<div className="mt-1.5">` — the
anchor stays `inline-flex` so the ↗ glyph keeps its baseline — with the reason
written next to it and a test (`keeps the website link off the "Add a
description" line`) that asserts the two are not siblings in one inline run.

## Judgement calls this pass made

Recorded because the plan did not specify them.

- **Client-side normalisation exists.** The plan specified only the wire-boundary
  rejection. A form that 400s on `casavostra.com` is a form people will fight, so
  `normalizeWebsiteUrl` adds the scheme — but only when there is none, and it
  validates with the *shared* schema so the two can never disagree.
- **`displayHost` moved packages-internally** rather than being imported from
  `BrandIdentity` by `BrandCard`. Three existing assertions moved with it.
- **The card shows the host, the hub shows a link.** Same fact, two registers,
  for the nested-anchor reason above.
- **No CHECK constraint on `website_url`.** Reasoning above.

## Left for later, named rather than buried

- **`RenameDialog` is now called `Rename brand` and edits three fields.** It has
  edited the description under that title since 0.9.0, and the website makes the
  drift harder to ignore — but retitling it means retitling `EntityMenu`'s
  `Rename` item too, which is a naming decision across three resource types and
  outside this pass. Flagged, not fixed.
- **No `websiteUrl` in the agent's system prompt.** Consistent with the plan's
  open question about whether the agent sees structured brand facts at all; a
  brand's website is data the model still cannot read.
- **No reduced-motion pass and no keyboard walk.** Both themes were shot; focus
  order was not — the same debt 1.8.0 logged.
- **1.6.0's brand switcher is now *incidentally* screenshotted** (it is in the
  header of every hub shot this pass took, populated, because these ran signed
  in against a real workspace — which is exactly what 1.8.0's auth-less demo
  route could not do). Its long-name truncation and 30-brand menu placement are
  still unobserved.

**Untouched:** `packages/agent` (beyond two fixture lines), `adapters/*`,
`miniApps.ts`, `editor/proseMirrorSchema.ts`, `.env.example` (no new env keys, so
the drift guard has nothing to say), and `docs/changelog.md` — Stage 1 ships as
1.9.0 with 1B.
